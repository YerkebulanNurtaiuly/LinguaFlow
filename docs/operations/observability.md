# Observability (OPS-04)

What LinguaFlow tells you about itself in production, and how to switch each part on.

| Signal | Where it comes from | Where it goes |
|---|---|---|
| Logs | the backend writes ECS JSON lines to stdout in the `prod` profile | Render's log view, or a log drain |
| Metrics | Micrometer, `GET /actuator/prometheus` (bearer `METRICS_TOKEN`) | Prometheus and Grafana, or any Prometheus-compatible service |
| Backend errors | Sentry Java SDK, on when `SENTRY_DSN` is set | Sentry |
| Browser errors | `frontend/src/lib/errorReporting.ts` → `POST /api/client-errors` | the backend log (logger `linguaflow.client`), and Sentry through it |
| Uptime | `.github/workflows/uptime.yml`, every 10 minutes | a failed Actions run, emailed to the repository owner |

Nothing here sends prompts, answers, passwords or tokens anywhere (SEC-02).

## Logs

In the `prod` profile the console log is Elastic Common Schema JSON
(`logging.structured.format.console: ecs`), one object per line, with
`service.name=linguaflow-backend`, `service.version` (the commit, `APP_VERSION`) and
`service.environment`. Every request line carries the `correlationId` from the MDC, which is
also in every error body, so a learner's error report leads straight to its log lines.

Render keeps the logs for a limited time. To keep them longer or search them, add a log
stream (Dashboard → Workspace settings → Log streams) to a service such as Better Stack,
Datadog or Grafana Cloud Logs; they read the JSON as fields.

Dev and test keep Spring's readable console format.

## Metrics

`/actuator/prometheus` is served by the backend only to a caller sending
`Authorization: Bearer <METRICS_TOKEN>`; without a token configured it always answers 401.
The token is generated by Render (`render.yaml`). The backend is a private service, so a
scraper has to run on the same Render private network (for example a small Prometheus or
Grafana Alloy private service pointed at `linguaflow-api-*:8080`), or push to a hosted
Prometheus through Alloy with `remote_write`.

Every metric carries `application=linguaflow`. Besides the JVM, HTTP (`http_server_requests`,
with histogram buckets for percentiles), Hikari and Tomcat defaults, the app adds:

| Metric | Tags | Meaning |
|---|---|---|
| `linguaflow_ai_calls_seconds` (timer) | `use_case`, `model`, `outcome` | every LLM call; `outcome` is `success` or the failure kind (`timeout`, `invalid_output`, …) |
| `linguaflow_ai_tokens_total` | `use_case`, `model`, `type` | input, output, cache_read and cache_write tokens |
| `linguaflow_ai_cost_usd_total` | `use_case`, `model` | the cost from `AiPricing` |
| `linguaflow_ai_refused_total` | `use_case`, `reason` | calls refused before reaching the provider: `quota` or `circuit_open` |
| `linguaflow_ai_cache_total` | `use_case`, `result` | shared AI cache lookups, `hit` or `miss` |
| `linguaflow_ai_jobs` (gauge) | `status` | jobs in `ai_jobs` per status, read at most every 15 s |

### Dashboards

`ops/observability/` holds a Prometheus config and two provisioned Grafana dashboards:

- **LinguaFlow — AI:** cost over 24 h, calls, error rate, queued jobs, calls per minute,
  failures and refusals, p50/p95 latency, tokens, cost per hour, cache hit ratio and the job
  queue.
- **LinguaFlow — API and JVM:** request rate, 5xx ratio, p95, heap, responses by status,
  latency per endpoint, 4xx, JVM threads and memory, Hikari pool and GC.

Locally:

```bash
docker compose --profile observability up --build
```

Prometheus is on http://localhost:9090 and Grafana on http://localhost:3001 (anonymous
viewing; `admin`/`admin` to edit). The local backend uses the public token
`local-metrics-token`. The dashboard JSON files can be imported into any Grafana with a
Prometheus data source whose UID is `prometheus`.

Suggested alerts: AI error rate above 20% for 10 minutes, any `circuit_open` refusals, more
than 100 queued AI jobs for 15 minutes, 5xx ratio above 2%, and daily AI cost above budget.

## Error tracking

### Backend

`io.sentry:sentry-spring-boot-4-starter` and `sentry-logback` are always on the classpath and
do nothing until `SENTRY_DSN` is set. With a DSN:

- every `ERROR` log line becomes a Sentry event and `INFO` and above become breadcrumbs;
  unhandled exceptions are logged by `GlobalExceptionHandler`, so they arrive this way;
- Sentry's own MVC exception resolver is filtered out (`SentryConfig`), because
  `GlobalExceptionHandler` already turns expected errors (404, 400, 409…) into responses,
  and those aren't bugs;
- `send-default-pii` is off: no IP addresses, cookies or request bodies;
- events carry the environment (`SENTRY_ENVIRONMENT`) and release (`APP_VERSION`, the
  commit), so a regression points at its deploy.

To set it up: create a Java project in Sentry, copy its DSN and enter it as `SENTRY_DSN` on
`linguaflow-api-staging` and `linguaflow-api-production` in the Render Dashboard. The DSN is
a credential; never commit it.

### Frontend

The production build reports render crashes (`AppErrorBoundary`, the route error page),
uncaught errors and unhandled promise rejections to `POST /api/client-errors`. The report is
small: the kind, message, stack, page path (no query or fragment) and the release from
`/version.txt`. Each distinct message is sent once per page load, at most 10.

The endpoint is public, rate-limited per IP (30 a minute,
`linguaflow.rate-limit.client-errors`), validates lengths, removes control characters,
redacts emails and long digit runs, and logs one `ERROR` line on the logger
`linguaflow.client`. That line reaches Sentry like any other error, so no Sentry key ships in
the browser bundle and the CSP stays `connect-src 'self'`.

## Uptime

`.github/workflows/uptime.yml` checks `/healthz` (nginx) and `/actuator/health` (backend and
database) every 10 minutes for the environments whose repository variables
`PRODUCTION_URL` and `STAGING_URL` are set, retrying three times before failing. GitHub
emails the repository owner about failed scheduled runs. Scheduled runs can start several
minutes late and GitHub pauses them in repositories without activity for 60 days, so for
paging use a dedicated monitor (Better Stack, UptimeRobot, Grafana Synthetic Monitoring)
on the same two URLs.
